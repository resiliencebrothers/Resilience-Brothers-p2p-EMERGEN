# RCA — Cloudflare 520 on p2p.resiliencebrothers.com (origin p2p-exchange-hub-2)

## Problem statement
Users saw Cloudflare **520** on https://p2p.resiliencebrothers.com starting ~2026-10-20 10:45 UTC. The last deploy (run `003680b6`, 2026-10-19 00:48 UTC) succeeded and the site worked for 6+ hours afterward. So this was a **runtime origin failure hours after a healthy boot**, not a mid-flight/failed deploy. Correct on all counts.

## Verdict: transient infra event — ALREADY SELF-RECOVERED
The origin is healthy again as of this investigation. No action is required to "bring it back" — it came back on its own at ~10:49 UTC once the rescheduled pods became ready.

## What the evidence shows NOW (live)
- `GET /api/` → **200** `{"service":"Resilience Brothers P2P","status":"ok"}` (backend origin answering).
- Both replicas `Running`, `ready: true`, **`restart_count: 0`**.
- Backend log: `Uvicorn running on http://0.0.0.0:8001` + `Application startup complete` → uvicorn is listening on 8001 and accepting connections.
- MongoDB healthy: scheduled DB jobs (`run_cash_box_sync`, `run_credit_recovery`, `run_ipv_count_recovery`, `run_daily_fx_snapshot`) all "executed successfully"; `/api/auth/me`, `/api/qr-poster`, `/api/system/defensive-mode` all 200. No DB connection/pool errors in logs.

## Root cause (proven)
A **Kubernetes node consolidation / scale-down** evicted the running backend pod, and the replacement pods took several minutes to become ready — dominated by a slow cold image pull. During that gap there was no ready origin, so Cloudflare returned 520.

Timeline from pod events (run `003680b6`, cluster deployment-cluster-04):
- `10:41:28Z` — pod `...-57c67bb444-p7j54` → `Evicted pod: Underutilized` + `Killing`. (This is node consolidation of an underutilized node, NOT OOM and NOT disk-pressure.)
- `10:41:28Z` — replacement pod `...-7977m` scheduled; `10:41:33Z` began pulling image.
- Image pull took **4m47s** (image size 836 MB) → container `Started` only at `10:46:20Z`; uvicorn `Application startup complete` at `10:47:17Z`.
- `10:46:23Z–10:47:13Z` — `Startup probe failed: HTTP probe failed with statuscode: 503` ×11 (nginx up, uvicorn not yet listening).
- `10:48:16Z` — second pod `...-kdcdx` scheduled (image pull 23.6s), startup complete `10:49:08Z`; startup-probe 503 ×5 during its boot.
- Backend/nginx logs during the gap: `connect() failed (111: Connection refused) while connecting to upstream ... http://127.0.0.1:8001/health` at 10:48:46–10:49:06 — the proxy had no backend to talk to → Cloudflare 520.

Because the app runs **tier_0 (2 replicas)** and both replicas were rescheduled in the same consolidation window (10:41 and 10:48), there was no surviving replica to serve traffic during the cold-pull gap → full origin outage for a few minutes.

## Hypotheses explicitly RULED OUT (evidence)
- **Disk full (logs/uploads/temp)** — ruled out. Eviction reason was `Underutilized` (node consolidation), not `DiskPressure`/ephemeral-storage. No disk-write errors in logs. Proof uploads go to **R2** (`[storage] R2 ready — bucket=resilience-p2p-proofs`), not local disk.
- **OOMKilled / memory leak** — ruled out. No `OOMKilled`, no exit code 137, `restart_count: 0` on both pods.
- **Crash-loop** — ruled out. No CrashLoopBackOff; pods booted cleanly and stayed up.
- **uvicorn hung / not listening** — only true transiently during the 10:41–10:49 reschedule; it is listening on 8001 now.
- **MongoDB connection drop / pool exhaustion** — ruled out. DB-backed jobs and API routes return success; no Mongo errors.
- **Code 500** — ruled out. Same image serves 200s now and in preview; nothing changed in the source.

Note: the `GET /health → 404` lines are benign — the app exposes routes under `/api`, not `/health`; a 404 is a non-5xx response that satisfies the readiness check (proves uvicorn is accepting connections).

## Remediation
1. **Now:** nothing — origin self-recovered at ~10:49 UTC and is serving 200s. If a user still sees 520, it is stale Cloudflare edge/browser cache; hard-refresh / retry.
2. **Prevent recurrence (Platform/Emergent):** node consolidation evicted the backend with no disruption budget protecting a surviving replica, and the replacement endured a ~5-minute cold image pull. Mitigations are platform-side: (a) honor a PodDisruptionBudget so consolidation never takes all replicas of an app at once, and (b) pre-warm / cache the app image on target nodes to avoid multi-minute cold pulls that extend the origin gap.
3. **Optional hardening (Code/E1):** the runtime image is ~836 MB, which is what makes the cold pull ~5 min. Slimming the image (smaller base, fewer build artifacts) shortens the reschedule gap and the 520 window. Secondary contributor only.
4. **Optional (User):** tier_0 caps at 2 replicas with HPA disabled. A higher tier with more replicas spread across nodes reduces the chance that a single consolidation event removes all serving pods simultaneously. Not the cause — a resilience trade-off.
